## Description

Found in T-001 on 2026-09-26: upstream Open Opal builds and runs on mudmini but can't open
Chris's C1. His camera behaves differently from the one upstream (and jtannahill) built against:

| | Upstream / jtannahill's C1 | Chris's C1 |
|---|---|---|
| USB ID while a webcam | `03e7:f63d` → depthai state `FLASH_BOOTED` | `03e7:f63b` → state `BOOTED` |
| Bootloader version | 0.0.15 | **0.0.0** |
| Webcam modes | 720p–4K @30 | 1080p @60 only |

What happens at power-on (read-only watcher, `build/replug-watch.log`): the camera sits in
`BOOTLOADER` for ~5.4 s, drops off the bus for ~0.8 s, then comes back `BOOTED` (stock webcam).
Upstream's app does catch it in that window, then depthai stops:

```
open attempt 1 failed: Bootloader version 0.0.2 required to send request 'UsbRomBoot'. Current version 0.0.0
```

depthai only boots bootloaders ≥ 0.0.12 directly. For older ones it sends `UsbRomBoot`
(command 0: restart into the chip's built-in USB boot mode, after which depthai loads its
firmware into RAM the normal way). But it refuses to send even that to a bootloader claiming
< 0.0.2. This ticket sends that one command itself, then hands over to upstream's normal
boot path.

**Why this is safe to try (evidence, not hope):**
- Command 0 carries no payload, so it has nothing to write. The flash-write command is 2 and
  needs an image.
- This bootloader speaks the standard protocol. It answered request 3
  (`GET_BOOTLOADER_VERSION`), and depthai's parser accepted the reply, which it rejects unless
  the response-type number matches (`DeviceBootloader.cpp` `parseResponse`). Numbering on both
  sides lines up with `depthai-bootloader-shared/Bootloader.hpp`.
- Everything lands in RAM; a replug restores stock (`CLAUDE.md § Rules`).

## What to build

1. In `Sources/OpalBridge/OpalBridge.cpp`, add a small helper, e.g.
   `static bool kickLegacyBootloaderToRom(const dai::DeviceInfo& info)`, that:
   - connects **without booting**: `std::make_shared<dai::XLinkConnection>(info, X_LINK_BOOTLOADER)`
     (the same call `DeviceBootloader.cpp:409` uses);
   - opens `dai::XLinkStream(conn, dai::bootloader::XLINK_CHANNEL_BOOTLOADER,
     dai::bootloader::XLINK_STREAM_MAX_SIZE)`;
   - sends `dai::bootloader::request::GetBootloaderVersion{}`, reads and parses a
     `dai::bootloader::response::BootloaderVersion` (check `cmd` matches and the size is right,
     like `parseResponse`). If the reply doesn't parse, **return false and send nothing else**;
   - **only if** the version is below 0.0.2, writes `dai::bootloader::request::UsbRomBoot{}`
     (raw struct, like `sendRequest`), then does one `read()` to wait for the link to drop
     (exceptions ignored, like `bootUsbRomBootloader`);
   - logs each step through `bootLog(...)` in plain words.
2. In `opal_open`, when the matched `info.state == X_LINK_BOOTLOADER`, call the helper before
   constructing `dai::Device`. If it kicked, poll `XLinkConnection::getAllConnectedDevices()`
   for up to 10 s for the device to come back as `X_LINK_UNBOOTED` (same mxid; if the mxid
   differs in ROM mode, take the single UNBOOTED `03e7` device and log that). Then construct
   `dai::Device` from that info. If it didn't kick (bootloader ≥ 0.0.2), do nothing: upstream's
   path runs unchanged.
3. Comment block above the helper: why (this C1's bootloader reports 0.0.0), what it sends
   (command 0 only), what it never sends, and a pointer to this ticket. Written so the change
   can go upstream as-is.
4. Rebuild (`xcodebuild` Release as in T-001), then the hardware test (§ Verification,
   human-assisted part).
